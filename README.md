# EVE Healthcare - Backend Engineering Assignment

This is a backend service for diagnostic test bookings and simulated payments, built using **FastAPI** and **SQLAlchemy**.

## Features Included
1. **Authentication:** User signup and login with JWT-based authentication.
2. **Diagnostic Centres & Tests:** APIs to manage centres and the tests they offer.
3. **Booking System:** Authenticated users can book tests.
4. **Simulated Payment Service:** A mock endpoint to simulate payments.
5. **Payment Webhook:** An idempotent webhook endpoint to process simulated payment updates.
6. **Edge Cases Handled:** Validates user ownership for bookings, prevents repeat webhook processing, and prevents booking already confirmed tests.
7. **Bonus Features Implemented:** Docker & docker-compose support, interactive Swagger/OpenAPI documentation (auto-generated by FastAPI).

## How to run the project locally

### Option 1: Using Docker (Recommended)
This option will set up the FastAPI application alongside a PostgreSQL database.

1. Ensure you have Docker and Docker Compose installed.
2. Run the following command in the root directory:
   ```bash
   docker-compose up --build
   ```
3. The API will be available at `http://localhost:8000`.

### Option 2: Using Python natively (with SQLite)
This option uses a local SQLite file database for easy setup.

1. Create and activate a virtual environment:
   ```bash
   python -m venv venv
   source venv/bin/activate  # Or `.\venv\Scripts\activate` on Windows
   ```
2. Install dependencies:
   ```bash
   pip install -r requirements.txt
   ```
3. Run the server using Uvicorn:
   ```bash
   uvicorn eve_health.main:app --reload
   ```
4. The API will be available at `http://localhost:8000`.

## API Endpoints and Example Requests

You can view the full interactive API documentation by visiting `http://localhost:8000/docs` while the server is running.

Here is a summary of the main endpoints:

- **POST `/users/signup`** - Register a new user.
- **POST `/users/login`** - Login and obtain a JWT access token.
- **POST `/centres/`** - Create a diagnostic centre.
- **POST `/centres/{centre_id}/tests`** - Add a test to a centre.
- **GET `/centres/`** - List all centres and their available tests.
- **POST `/bookings/`** - Create a booking (Requires Auth).
- **GET `/bookings/`** - List your bookings (Requires Auth).
- **POST `/payments/`** - Simulate a payment (Requires Auth). Will randomly trigger SUCCESS or FAILED to the webhook.
- **POST `/payments/webhook/`** - Webhook to accept payment statuses. It relies on an `event_id` to ensure idempotency.

## Database / Schema Design

The database consists of the following core tables:
- **`users`**: Stores user authentication and profile details.
- **`centres`**: Stores diagnostic centres (name, location).
- **`diagnostic_tests`**: Stores tests offered by centres. Links to `centres` via `centre_id`.
- **`bookings`**: Stores test appointments. Links to `users`, `diagnostic_tests`, and `centres`. Has a `status` field (PENDING, CONFIRMED, FAILED, CANCELLED).
- **`payment_events`**: Used to track webhook idempotency by storing a unique `event_id` for every processed webhook hit.

## Important Assumptions Made
- A test is strictly bound to a single centre. If multiple centres offer the same test, they are recorded as separate entries under each centre.
- Prices are floating-point numbers. In a production real-world scenario, storing them as integers (cents) using `Numeric` types is preferred to prevent precision loss.
- Simulated payments directly hit the webhook via a background HTTP task to emulate real-world provider callbacks.
- Passwords are securely hashed using bcrypt.
